# LLMs Get Lost In Multi-turn Conversation

## 基本信息

- Title: LLMs Get Lost In Multi-turn Conversation
- Authors:
- Year: 2026
- Conference / Journal: ICLR


## 一句话总结

这篇论文研究了大语言模型在多轮对话中是否会随着对话轮次增加而出现理解偏差、上下文遗忘或任务执行能力下降的问题。




## 论文基本信息

论文研究的是：
为什么 LLM 在单轮、完整指令下能够完成任务，但同样的信息被拆成多轮、逐步提供后，性能会明显下降？

作者特别想区分两种可能：
1. 能力下降：模型本身不会做了；
2. 可靠性下降：模型有能力做对，但每次表现不稳定。
论文的核心答案是：
多轮场景中的主要问题不是能力大幅下降，而是可靠性显著下降。模型一旦在早期对不完整信息作出错误假设，后续往往会沿着错误方向继续生成，而不是重新理解问题。

作者把这种现象称为：
Lost in Conversation：在对话中迷失

## 核心方法

作者可能通过构造多轮对话任务，观察模型在不同轮次、不同信息位置、不同任务复杂度下的表现。

1. 任务
作者选择了 6 类生成任务：
- Code：写代码
- Database：生成 SQL
- Actions：生成 API 调用
- Math：数学题
- Data-to-Text：根据表格生成文本
- Summary：多文档摘要
总计约 600 条指令，每类约 90-120 条。
2. 三种主要输入方式
设置	含义
FULL	完整指令一次性给出，作为单轮基线
CONCAT	把拆开的信息重新拼到一个 prompt 中，仍然单轮
SHARDED	信息拆成多个 shard，在多轮中逐步给出


这个设计非常关键。
- FULL 与 SHARDED 的任务和信息相同；
- CONCAT 用来检验问题是不是来自改写；
- 如果 CONCAT 基本正常，但 SHARDED 明显变差，就说明主要问题来自多轮逐步交互，而不是文本改写或信息丢失。
3. 实验规模
主实验包括：
- 15 个 LLM
- 6 类任务
- 约 600 条指令
- 每个条件重复模拟 10 次
- 总计超过 20 万次模拟对话
用户由 GPT-4o-mini 模拟。用户每轮最多透露一个 shard，模型每轮自由回答。

## 主要贡献

1. 系统分析了 LLM 在多轮对话中的能力退化问题。
2. 指出模型可能无法稳定整合分散在多轮上下文中的信息。
3. 为改进长上下文建模、多轮指令跟随和对话式智能体提供了参考。

## 实验与结果

结论 1：多轮 SHARDED 的平均性能下降约 39%
所有模型在 SHARDED 设置下都出现下降。
也就是说：
同样的任务、同样的信息，仅仅把完整要求拆成多轮逐步给出，就可能让模型表现明显变差。

结论 2：真正严重的是不可靠性增加
论文把下降拆成两部分：
- Aptitude：能力上限下降约 16%
- Unreliability：不可靠性增加约 112%
这说明模型并不是完全失去了解题能力。
更准确地说：
模型有时仍然能够给出正确答案，但不同运行之间波动变得非常大。

固定一条指令时，多轮设置下最好和较差模拟结果平均相差约 50 个百分点。
结论 3：强模型也不能避免这个问题
GPT-4.1、Gemini 2.5 Pro、Claude 3.7 Sonnet 等强模型，在单轮中表现更好，但进入 SHARDED 多轮设置后，同样出现明显的可靠性下降。
因此论文不是在说：
只有小模型会迷失。

而是在说：
模型能力越强，并不意味着它具备稳定的多轮交互能力。
## 我的理解

我认为这篇论文的重要性在于，它提醒我们不能只看 LLM 在单轮问答中的表现。  
在真实应用中，用户往往会不断修改需求、补充约束、纠正模型回答。  
如果模型不能稳定追踪多轮上下文，就很难可靠地完成复杂任务。

这也说明，多轮对话能力不只是“上下文窗口足够长”这么简单。  
模型还需要真正理解信息之间的关系，并知道哪些历史信息仍然重要。

## 优点

- 关注真实应用中非常常见的问题
- 对评估 LLM 的对话能力有实际意义
- 有助于发现单轮 benchmark 难以暴露的问题

## 局限性

1. 用户是 LLM 模拟的，不是真实用户
用户模拟器比较理想化：
- 每轮最多提供一个 shard；
- 最后一轮通常会提供完成任务所需的全部信息；
- 不会真正表现出人类的犹豫、误解、放弃或情绪。
所以实验结果不能直接等同于真实人机对话。
不过作者认为，这种模拟通常会低估真实场景中的不可靠性。
2. 任务主要是分析型任务
实验集中在：
- 代码
- 数学
- SQL
- 摘要
- 表格描述
没有充分覆盖：
- 创意写作
- 开放式讨论
- 没有明确标准答案的任务
3. 只研究英文文本任务
论文没有验证：
- 中文等其他语言；
- 图片、音频、多模态多轮对话；
- 复杂工具调用链。
4. SHARDED 设计可能偏人工
每轮只加入一个 shard，可能比自然人类交流更极端。
因此它更像是：
一个受控的多轮可靠性压力测试，而不是完整模拟真实对话。
## 可以进一步思考的问题

- LLM 为什么会在多轮对话中迷失？
- 是上下文太长导致的，还是模型没有学会有效检索历史信息？
- RAG、记忆机制或 agent 框架能否缓解这个问题？
- 多轮对话 benchmark 应该如何设计才合理？
- 长上下文模型是否真的解决了多轮对话问题？
