#  Test-Time Compute of Process Reward Models via GeGenPRM 

## 一、基本信息

- **论文标题**：GenPRM: Scalingnerative Reasoning
- **会议/年份**：AAAI 2026
- **研究方向**：大语言模型、数学推理、过程监督、奖励模型、测试时计算扩展
- **核心方法**：GenPRM，生成式过程奖励模型
- **主要目标**：让模型不仅能判断数学题最终答案是否正确，还能检查推理过程中的每一步是否可靠。

---

## 二、一句话介绍

这篇论文提出了 **GenPRM**，一种会先分析、再验证、最后判断推理步骤对错的生成式过程奖励模型，用来提升大语言模型在数学推理任务中的可靠性。

---

## 三、专业术语

### 1. PRM：过程奖励模型

PRM，即 Process Reward Model，用来判断解题过程中每一步推理是否正确。它关注的是“过程”，而不是只看最终答案。

### 2. ORM：结果奖励模型

ORM，即 Outcome Reward Model，只判断最终答案是否正确。相比 ORM，PRM 更适合发现推理中间的错误。

### 3. GenPRM：生成式过程奖励模型

传统 PRM 通常只输出一个分数，而 GenPRM 会生成分析过程、进行代码验证，并最终给出 Yes/No 判断。

### 4. CoT：思维链

CoT，即 Chain-of-Thought，指模型在回答或判断前先写出中间推理过程。本文利用 CoT 帮助 GenPRM 更准确地判断推理步骤。

### 5. Code Verification：代码验证

代码验证指让模型生成 Python 代码来检查某一步推理是否成立。它可以减少单纯自然语言判断带来的误差。

### 6. Test-Time Scaling：测试时计算扩展

测试时计算扩展指模型在推理阶段多花计算资源，例如多次生成、多次验证、多数投票，从而提高准确率。

### 7. RPE：相对进展估计

RPE，即 Relative Progress Estimation，用来判断某一步推理是否让解题过程更接近正确答案。它比较加入当前步骤前后的成功率变化，而不是只看当前步骤之后能不能做对。

---

## 四、核心方法

本文的核心思想是：**把 PRM 从一个简单打分器，变成一个会解释、会验证、会判断的推理检查器。**

传统 PRM 的形式大致是：

```text
题目 + 当前步骤 → 分数
```

GenPRM 的形式则是：

```text
题目 + 当前步骤 → 自然语言分析 → 代码验证 → Yes/No 判断
```

作者认为，传统 PRM 只输出分数，不解释原因，也难以利用大语言模型本身的生成能力。GenPRM 通过生成式推理，让模型在判断前先“想清楚为什么”。

在训练数据构造方面，论文提出了 RPE 方法。传统方法通常从某个中间步骤继续生成多个答案，再看最终正确率。但这可能会误判，因为最终是否正确不仅取决于当前步骤，还取决于后续模型能力。RPE 则关注当前步骤是否带来了“相对进展”：如果加入这一步后，模型更容易得到正确答案，那么这一步更可能是有益的。

数据构造流程大致包括：

1. 使用 MATH 数据集中的数学题；
2. 用 Qwen2.5-7B-Instruct 生成分步解答；
3. 对每一步做 Monte Carlo 估计；
4. 用 RPE 生成步骤标签；
5. 用 QwQ-32B 生成分析和代码验证；
6. 用 LLM-as-a-judge 进行一致性过滤；
7. 最终得到约 23K 条高质量训练样本。

---

## 五、实验结果

论文主要做了三类实验。

### 1. ProcessBench 实验

ProcessBench 用来评测模型发现数学推理错误步骤的能力。结果显示，GenPRM 明显优于许多已有 PRM。

其中比较有代表性的结果是：

- GenPRM-1.5B 通过 Maj@8 超过 GPT-4o；
- GenPRM-7B 通过 Maj@8 超过 Qwen2.5-Math-PRM-72B；
- GenPRM 只使用约 23K 训练数据，却取得了很强的效果。

这说明 GenPRM 的优势并不只是来自模型规模，而是来自生成式推理和测试时扩展的设计。

### 2. Best-of-N 实验

在 AMC23、AIME24 等数学任务上，作者让模型生成多个候选答案，再用 GenPRM 选择最可靠的答案。实验表明，GenPRM 比多个基线 PRM 更善于选出正确解答。

### 3. Critique Refinement 实验

作者还测试了 GenPRM 作为 critic 的能力，即让它找出错误步骤并给出反馈，再让原模型修改答案。结果显示，多轮修改后模型表现持续提升，说明 GenPRM 不只是能打分，也能起到“批改老师”的作用。

## 六、优点与缺点

### 优点

1. **思路清晰**：将 PRM 从打分器升级为生成式检查器。
2. **可解释性更强**：GenPRM 会生成分析和验证过程，而不是只给分数。
3. **RPE 方法有启发性**：它关注当前步骤是否推动了解题进展。
4. **测试时扩展效果明显**：多次验证和多数投票可以显著提升性能。
5. **实验结果有说服力**：在找错、选答案、批改修改等场景都有提升。

### 缺点

1. **主要集中在数学任务**：在代码、医学、法律、开放问答等任务上的效果还需要验证。
2. **代码验证适用范围有限**：不是所有推理都能方便地转化为 Python 检查。
3. **数据构造成本较高**：需要多次采样、RPE 计算、强模型生成 rationale 和一致性过滤。
4. **测试时计算成本增加**：Maj@8 等方法虽然效果好，但会消耗更多 token 和推理时间。

---

## 七、可借鉴的思路

这篇论文最值得借鉴的是“过程监督”的思想。很多任务不能只看最终结果，还应该检查中间过程是否可靠。

可以借鉴的方向包括：

1. **先解释，再判断**：让模型在给出结论前先说明理由。
2. **引入工具验证**：用代码、检索、数据库或测试用例辅助模型判断。
3. **关注相对进展**：评价一个步骤时，不只看它本身是否正确，还要看它是否让任务更接近目标。
4. **让检查器也多次思考**：不仅回答模型可以多生成，验证模型也可以多次判断并投票。
5. **从裁判转向老师**：好的模型不应该只说“错了”，还应该指出错在哪里、为什么错、如何改。

---

## 八、个人读后感

我认为这篇论文的价值在于，它重新定义了过程奖励模型的作用。传统 PRM 更像一个评分器，而 GenPRM 更像一个会分析和批改的老师。

在大语言模型推理任务中，最终答案正确并不一定代表推理过程可靠。因此，检查中间步骤非常重要。GenPRM 通过 CoT、代码验证和测试时扩展，让过程监督变得更可解释、更灵活，也更实用。

这篇论文给我的启发是：未来的大模型系统中，不应该只有“回答者”，还应该有强大的“检查者”。而这个检查者最好不是简单打分，而是能够解释、验证、反馈和帮助修改。
